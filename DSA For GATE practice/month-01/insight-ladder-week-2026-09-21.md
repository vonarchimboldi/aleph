# Insight ladder: September 21–25 production brief

## Identity and approved decisions

Month 1, Week 4; five weekday sessions, 120 minutes each, C11 or Python 3. The instructor approved the easy/medium/hard/medium/easy conceptual ladder and asked to build it out. This replaces the usual three guided LeetCode labs with one original main task and an optional variation per day. Difficulty rises through conceptual insight and changed assumptions. No extra weekend work is added.

## Learning target and prerequisites

Use the September sorting sprint and September 14–18 ladder as prerequisites: arrays, sorting, two pointers, invariants, counting, and binary search on answers. Learn to formulate a claim, test its assumptions, and justify discarded candidates before implementing. This is an approved curriculum progression, not a diagnosis from new learner submissions.

## Timing and success criteria

10 minutes retrieval; 90 minutes main/optional practice; 20 minutes explanation and review. Keep independent, hinted, and method-supplied insight distinct. Count code solves separately from reasoning variations. A main solve requires correct constrained code, tests, and explanation. No quota, and no automatic assumption of independence.

## Daily discovery briefs

### Day 1: How far does disorder spread? (Easy)

- Motivating task and contract: Return the shortest inclusive interval [l,r] whose sorting makes the entire integer array nondecreasing. Return [-1,-1] if it is already sorted (including empty or singleton input). Do not modify the input. Arrays may contain duplicates; n <= 200,000 and values lie between -1,000,000,000 and 1,000,000,000. Require O(n) time and O(1) auxiliary space. First develop a slower baseline for small inputs.
- Transfer: Instead of sorting, you may reverse one contiguous interval. Decide whether that can make the array nondecreasing, and return any valid interval, or IMPOSSIBLE. Already sorted arrays return [-1,-1]. An O(n log n) solution with O(n) storage is acceptable for this optional task. Does the shortest sorting interval always work when reversed? Give a counterexample.
- Core state, invariant, correctness, and complexity: A sorted-copy baseline finds the first and last mismatches in O(n log n) time and O(n) space. For the required method, scan left to right maintaining the maximum of the prefix. Whenever a[i] is smaller than that maximum, set r=i. Scan right to left maintaining the minimum of the suffix; whenever a[i] is larger, set l=i. If no violation occurs, return [-1,-1]. Every right-hand violation requires any repair interval to reach at least that far right, and every left-hand violation forces it at least that far left. Outside these endpoints the elements have no inversion with later or earlier elements respectively. Sorting the middle therefore fixes all remaining inversions. Two scans cost O(n) time and O(1) space. Use strict inequalities so equals are not violations.
- Misconception to expose: Why might the first and last adjacent descents fail to identify the full interval? Explain why your final endpoints are necessary as well as sufficient.
- Essential traces: [1,3,2,2,4] gives [1,3]. [2,1] gives [0,1]. [2,2,2] gives [-1,-1]. Test a long ordered prefix and a small value near the end.
- Progressive hints: Compare the array with a sorted copy in your baseline. What do the first and last mismatching positions tell you? / When scanning left to right, what earlier value certifies that this position cannot stay outside the interval? / Maintain the maximum seen so far to find the last out-of-order position. Scan from the right with a running minimum to find the first.
- Repair trigger: an unjustified claim or failed boundary test. Drill: Trace running maxima and minima on [1,3,2,2,4], marking the evidence that forces each endpoint.

### Day 2: Which pairs count? (Medium)

- Motivating task and contract: Given an unsorted integer array and inclusive bounds L <= R, count index pairs i < j satisfying L <= a[i]+a[j] <= R. Equal values at different indices represent different pairs. n <= 200,000; values and bounds lie between -1,000,000,000 and 1,000,000,000. Require O(n log n) time; sorting a copy is allowed. In C, use 64-bit arithmetic for sums and counts. State the cost of sorting and its storage separately from your scan.
- Transfer: Count distinct unordered VALUE pairs instead of index pairs, in O(n log n) time. A pair (x,x) is allowed only if the input contains at least two copies of x. For [1,1,2,3] and [3,4], the answer is 2; for [2,2,2] and [4,4], it is 1. Explain why simply removing duplicates and running the original routine is insufficient.
- Core state, invariant, correctness, and complexity: Sort. To count pairs with sum <= T, place l at 0 and r at n-1. If a[l]+a[r] <= T, all r-l partners from l+1 through r work for l; add r-l and increment l. Otherwise no pair using r with any remaining left endpoint can work, so decrement r. Each step eliminates exactly the pairs just counted or proved invalid. Change <= to < to count sums strictly below L. Subtract countLess(L) from countAtMost(R). Each pointer moves O(n) times. Total time is O(n log n), with O(1) scan storage; a Python sorted copy uses O(n) storage. In C report the actual sorting implementation storage.
- Misconception to expose: Can one exact range be expressed using two easier counting questions? Why can your algorithm count a whole block of pairs without listing them?
- Essential traces: [1,1,2,3] with [L,R]=[3,4] gives 4. [2,2,2] with [4,4] gives 3. Empty and singleton arrays give 0. Also test negative numbers, L=R, and no valid pairs.
- Progressive hints: First solve an easier question: how many pairs have sum at most a threshold? / In sorted order, if the smallest remaining value plus the largest is small enough, which other partners for that smallest value also work? / Subtract the number of pairs with sum strictly below L from the number with sum at most R. Use separate strict/non-strict comparisons instead of relying on L-1.
- Repair trigger: an unjustified claim or failed boundary test. Drill: Enumerate the six index pairs of [1,1,2,3] and compare them with its distinct value pairs.

### Day 3: Select an answer you cannot list (Hard)

- Motivating task and contract: For every index pair i < j, form |a[i]-a[j]|. Return the kth smallest entry in this multiset of distances, counting equal distances separately. The rank k is one-based. Input: 2 <= n <= 200,000, integer values from -1,000,000,000 to 1,000,000,000, and 1 <= k <= n(n-1)/2. Do not build the full pair-distance list. Target time: O(n log n + n log(W+1)), where W=max(a)-min(a); O(n) auxiliary storage is allowed. Use wide counts and differences in C.
- Transfer: Reasoning task, not another coding quota: for [1,1,3,3], list all six distances. Explain why a counting function can jump past k and why testing whether its count equals k is wrong. Give the output for k=3. Distinguish a rank among occurrences from a rank among distinct values.
- Core state, invariant, correctness, and complexity: Sort a. Define C(d) as the number of index pairs with distance <= d. Start l=0. For each r, advance l while a[r]-a[l] > d, then add r-l. The valid left endpoints form a contiguous suffix before r; earlier endpoints are too far away. As r increases, l never needs to move left. Thus C takes O(n) time and O(1) scan space. Binary-search integers [0,W]: mid=lo+(hi-lo)//2; if C(mid)>=k set hi=mid, else lo=mid+1. Larger d includes every pair counted at smaller d, proving monotonicity. Initially W is feasible and 0 is a valid lower bound. Each update retains the first feasible integer and strictly shrinks the interval. When lo=hi, that integer is the kth distance. Sorting takes O(n log n), followed by O(n log(W+1)) work; W=0 needs no search iterations.
- Misconception to expose: If you cannot cheaply list the answers, what cheaper question about a proposed answer would let you rule out many possibilities?
- Essential traces: [1,3,1], k=1 gives 0; k=2 gives 2; k=3 gives 2. [4,4,4] gives 0 for every valid rank. [0,4,9], k=2 gives 5. Test the smallest and largest ranks.
- Progressive hints: Ignore selecting k for a moment. For a candidate distance d, can you count how many pairs have distance at most d? / Sort and process each right endpoint. Maintain the earliest left endpoint whose distance from it is at most d. How many pairs end here? / The count is nondecreasing in d. Find the first integer d whose count is at least k, not the first with count exactly k.
- Repair trigger: an unjustified claim or failed boundary test. Drill: Build C(d) by hand for [1,1,3,3] at d=0,1,2 before retrying the search.

### Day 4: How far apart can you place them? (Medium)

- Motivating task and contract: Choose exactly k positions from n distinct integer coordinates to maximize the minimum distance between any two chosen positions. Input is unsorted; 2 <= k <= n <= 200,000 and coordinates lie between -1,000,000,000 and 1,000,000,000. Return the optimal integer distance. Target O(n log n + n log(W+1)) time, where W=max(x)-min(x); sorting a copy is allowed. Use wide subtraction in C.
- Transfer: Now two specified coordinates must be selected. No new implementation is required: give a small counterexample showing why the original greedy checker cannot simply ignore the mandatory positions, or why checking whether its one chosen set includes both positions can wrongly reject a feasible distance. State precisely what your example disproves.
- Core state, invariant, correctness, and complexity: Sort coordinates. For a candidate d, choose the first position, then greedily the earliest position >= last+d until k are chosen or positions run out. Prove by induction that the greedy jth choice is no later than the jth choice of any feasible placement: this is true for j=1, and that placement's next choice is also far enough beyond the earlier greedy choice. Greedy therefore leaves at least as much room for future choices. Feasibility decreases as d increases. Search [0,W] with upper midpoint mid=lo+(hi-lo+1)//2; feasible implies lo=mid, otherwise hi=mid-1. The upper midpoint avoids a stall on a two-value interval. Return lo. It suffices to constrain adjacent chosen gaps since nonadjacent distances are sums of positive adjacent gaps. Each check is O(n); total is O(n log n+n log(W+1)), with sorting storage reported separately.
- Misconception to expose: What evidence makes a proposed distance feasible? Why is placing a selected point as early as possible safe in the original problem? Does a larger candidate distance become easier or harder?
- Essential traces: [1,2,4,8,9], k=3 gives 3. [0,10], k=2 gives 10. When k=n, test against the smallest adjacent gap after sorting. Include negative coordinates.
- Progressive hints: For a proposed distance d, try to decide only whether k positions can be chosen. / After sorting, choose the first coordinate and then each earliest coordinate at least d beyond the last chosen one. Compare these choices with those of any feasible placement. / Feasibility is true for smaller d and false for larger d. Search for the last feasible distance; use a midpoint that guarantees progress.
- Repair trigger: an unjustified claim or failed boundary test. Drill: Write down the direction of feasibility and trace the last-true search on an interval containing two integers.

### Day 5: Where should the split go? (Easy)

- Motivating task and contract: Split an array of nonnegative integers into two nonempty contiguous parts. Return (t,difference), where the left part contains the first t entries and difference is the absolute difference between the two part sums. Break ties by choosing the smallest t. Input: 2 <= n <= 200,000; entries are at most 1,000,000,000. Require O(n) total time; O(1) auxiliary space is achievable. Explain also whether the candidate split positions have an order property that permits searching after preprocessing.
- Transfer: Allow negative entries with absolute value at most 1,000,000,000. Give a counterexample to the order property used for searching. Then provide a correct O(n)-time, O(1)-space algorithm. For [4,-5,3,2], the answer is (3,0). Does your original linear scan need any change?
- Core state, invariant, correctness, and complexity: Compute total S. Scan t=1 through n-1, adding a[t-1] to P and evaluating |2P-S|. Retain a split only when its difference is strictly smaller than the best, preserving the earliest tie. This gives O(n) time and O(1) space. With nonnegative input, P is nondecreasing, so 2P>=S is a monotone predicate on valid split positions. In a precomputed prefix array, the first crossing and the preceding prefix value suffice to determine the smallest difference; if that preceding value repeats, choose its earliest index for the required tie. A plain scan avoids that extra tie handling. Building the prefix array costs O(n) time and O(n) space, so O(log n) search alone is not the total cost. Do not sort: contiguity belongs to the original order. Use 64-bit sums and absolute differences in C.
- Misconception to expose: Express both part sums using one total and one running quantity. Would building an auxiliary structure and then searching improve total time for this single query? Explain ties carefully.
- Essential traces: [1,2,3,4] gives (3,2). [0,0,0] gives (1,0). [1,1,1] gives (1,1). Test n=2 and zero runs, including repeated equally good splits.
- Progressive hints: Let S be the total and P the left sum. Rewrite the difference without summing the right side again. / The objective is |2P-S|. As t increases, does P ever decrease under the original assumptions? / A running-prefix scan already solves the task in O(n) time and O(1) space. A precomputed prefix array permits searching near half the total, but building it still costs O(n).
- Repair trigger: an unjustified claim or failed boundary test. Drill: List every valid split, prefix sum, and difference for [0,0,0] and [4,-5,3,2].
