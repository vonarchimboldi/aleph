SQL: aggregation grain, multiplicity and correlated subqueries

Round two · relative week 2 · unit 3 · application · 90-minute proposed session

Start by saying what one output row should represent

A query might need one row per employee or one row per team. Those are different outputs. GROUP BY collects rows sharing the chosen values. Each group produces an aggregate such as COUNT or SUM. Grouping by a unique employee ID creates groups containing only one employee.

Compute a team fact, then attach it to each employee

To display each employee with their team size, first group by TeamID and count the team’s rows. This produces one result per team. Join those results back to Employee using TeamID. Each employee then receives the count for the correct team. A small team of two employees makes the purpose of each step visible.

Follow a complete example

Employee has rows (e1,T),(e2,T),(e3,U). Grouping by TeamID gives T:2,U:1, but loses per-employee output. Joining these two group counts back on TeamID gives one row per employee with sizes 2,2,1.

R2-DBMS-03-A-Q1 · Start with one small step

For those three employees, what does GROUP BY EmpID with COUNT(*) return? Why is it not the requested team size?

Worked check · open after attempting

Every employee group contains one row, so all counts are 1. The grouping key defines the wrong grain.

Decide whether the inner query depends on the outer row

A subquery can compute one fixed threshold, such as the largest loan in branch X. Every outer row compares against that same threshold. A correlated subquery instead refers to the current outer row. To evaluate it, fix that outer row first and compute the inner result for that row.

R2-DBMS-03-A-Q2 · Put the pieces together

Give a SQL query returning each EmpID and its team size, using a grouped derived table. Assume TeamID is NOT NULL.

Worked check · open after attempting

SELECT E.EmpID,B.n FROM Employee E JOIN (SELECT TeamID,COUNT(*) AS n FROM Employee GROUP BY TeamID) B ON E.TeamID=B.TeamID;

Treat equal values explicitly

Suppose a condition counts balances strictly greater than the current balance and balances strictly smaller than it. Equal balances belong to neither count. List each distinct balance with its two counts, then apply the condition. If several rows share an accepted balance, each of those rows may appear in an ordinary SQL result. Do not replace the query with an informal ranking shortcut.

R2-DBMS-03-A-Q3 · Use the idea in an exam-style problem

Balances are 10,10,20,30. A query keeps an outer row when the count of strictly greater balances is at least the count of strictly smaller balances. Which rows remain? Show greater/smaller counts per distinct value.

Worked check · open after attempting

10:greater 2,smaller 0, so both 10 rows remain. 20:greater 1,smaller 2, reject. 30:greater 0,smaller 3, reject. Result has 2 rows.

How the ideas connect

Correct SQL depends on the unit counted and the row scope of each expression, not just on recognizing COUNT or GROUP BY.

State the intended output grain: one row per what? → Materialize groups or matching rows on a tiny instance. → For a correlated subquery, fix one outer row before evaluating its inner query. → Test ties and duplicates explicitly.

If a problem was difficult

  • Grouping by a unique employee ID when a team size is wanted
  • Joining a row to itself instead of its whole group
  • Replacing a strict comparison by a rank formula that mishandles ties
