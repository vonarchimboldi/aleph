Keys, foreign keys and ER-to-relation modelling

Round two · relative week 2 · unit 1 · application · 90-minute proposed session

A schema states rules for every legal table

A table’s current rows are one instance. Its schema states the columns and constraints every legal instance must satisfy. Seeing unique values in today’s data does not prove that a column must always be unique. A candidate key is a smallest set of columns guaranteed to identify a row.

A foreign key asks for a matching parent

Suppose Purchase.pid references Person.pid. A non-null Purchase.pid must match a Person.pid. Several purchase rows can reference the same person. The reference does not make Purchase.pid unique. A primary key must be unique and non-null. Other columns may permit NULL unless another constraint forbids it.

Follow a complete example

Person(pid PRIMARY KEY), Purchase(orderid PRIMARY KEY,pid REFERENCES Person) permits several purchases with the same pid. The foreign key requires a referenced parent when non-null; it does not make Purchase.pid unique.

R2-DBMS-01-A-Q1 · Start with one small step

With that schema, is Purchase.pid necessarily a candidate key? Give a legal instance showing your answer.

Worked check · open after attempting

No. Person has pid 1; Purchase may have (order 10,pid 1),(order 11,pid 1).

Test an operation by looking for a missing reference

Adding a parent gives child rows more possible matches. Removing a child removes one reference. Neither operation creates an unmatched reference by itself. Removing a referenced parent or adding a child without a parent can cause a violation. Read any stated cascading behavior before deciding whether the system rejects an operation.

R2-DBMS-01-A-Q2 · Put the pieces together

Ignoring unrelated constraints, which operations can never newly violate this foreign key: insert a parent, delete a child, delete a parent, insert a child? Explain.

Worked check · open after attempting

Insert a parent and delete a child. Deleting a referenced parent or inserting an unmatched child can violate it under restrictive referential handling.

Map each independent kind of information

An ER model describes entities, their attributes and their relationships. Give each entity a relation. A many-to-many relationship needs a relation containing the participating keys. A multivalued attribute needs a separate relation because one entity can have several values. Total participation means every entity participates at least once. It does not change a many-to-many relationship into a one-to-one relationship.

R2-DBMS-01-A-Q3 · Use the idea in an exam-style problem

Entities Student(sid,name,phone multivalued) and Course(cid,title) have a many-to-many Enrol relation. Under ordinary atomic relational mapping and no additional FDs, give the minimum relations and their keys.

Worked check · open after attempting

Student(sid,name), StudentPhone(sid,phone), Course(cid,title), Enrol(sid,cid): four. Keys sid; (sid,phone); cid; (sid,cid), respectively.

How the ideas connect

Constraints are universal schema rules; examples cannot create extra keys or nullability restrictions absent from the schema.

Identify each declared constraint and its table. → Distinguish a referenced primary key from a referencing foreign key. → Construct a legal counterexample to an alleged guarantee. → Map entities, many-to-many relations and multivalued attributes separately.

If a problem was difficult

  • Calling every foreign key a candidate key
  • Assuming every column is NOT NULL
  • Merging a multivalued attribute into a single atomic column
