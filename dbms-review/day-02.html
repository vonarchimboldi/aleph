Make every operator answer a small question

Selection keeps rows satisfying a predicate. Projection keeps named columns and, in classical relational algebra, removes duplicate tuples. A Cartesian product pairs every row from one relation with every row from another. A join is a product restricted by a matching condition. A natural join equates every shared attribute name, not only the column you happen to think of as the key. Rename columns when the intended matches differ.

Set union, intersection and difference require compatible relation schemas. Difference R−S means rows in R that are absent from S; reversing it changes the question. To check that all observed child IDs occur among parent IDs, form child IDs minus parent IDs and test emptiness. This is a statement about the current instance, not a proof that a declared constraint exists for every future instance.

“Some” and “every” are different query designs

Let Enrol(Student,Course) contain(Ada,DB),(Ada,AI),(Ben,DB),(Cy,AI), and let Required(Course) contain DB and AI. Asking for students with some required course gives all three students. Asking for every required course gives only Ada. For each candidate student, search for a required course they lack. Keep the student exactly when that search finds no counterexample.

In tuple-calculus notation, the every-course test has the form Student(s) AND NOT EXISTS c in Required for which no matching Enrol row exists. In logic, a universal statement can be rewritten as the absence of an existential counterexample. In algebra, one construction is to form all candidate student/course pairs, subtract actual qualifying pairs to expose missing pairs, project the failing students, then subtract those students from the candidate set.

Restrict candidate tuples to explicit database relations. This keeps the query finite and avoids asking for an unlimited complement over every possible string or number. A tuple-calculus comprehension returns qualifying output tuples; multiple witnesses for one output do not duplicate it under set semantics.

The empty-requirement case checks understanding

If Required is empty, every explicitly listed candidate student meets the every-required-course condition: there is no missing required course. This is vacuous truth. An existential “has some required course” query instead returns none. Always specify the candidate Student relation; otherwise the intended universe is ambiguous.

Two worked examples

Projection changes cardinality

R(A,B)={(1,x),(1,y),(2,y)}. Compare πA(R) with SELECT A FROM R.

Classical projection is the set{1,2}, size2. The ordinary SQL SELECT retains duplicate1 values and has3 rows; SELECT DISTINCT A corresponds to the set projection. The row counts differ because the semantics differ, not because one query is necessarily wrong.

Find missing pairs

Use Enrol and Required above. Explain an algebraic every-course query.

Candidate students are{Ada,Ben,Cy}. The student×required product has6 pairs. Missing pairs are(Ben,AI) and(Cy,DB). Their projected students are{Ben,Cy}; subtracting from candidates leaves{Ada}. This calculation makes the universal condition visible as absence of a missing pair.

Text version of the mind map
  • Operators: Rows, columns and matching; State set semantics explicitly.
  • Translate: Some → witness; Every → no counterexample.
  • Count: Output tuples, not witnesses; Natural join matches all shared names.
  • Check domain: Explicit candidate relations; Empty requirements test quantifiers.
