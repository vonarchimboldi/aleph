Begin with the objects and their rules

Suppose a college stores students and courses. A student can take many courses, and a course can have many students. Names are not reliable identities: two students may share a name. Give each student a StudentID and each course a CourseID. The relationship Enrolment records a pair of identities. If the model permits at most one enrolment per student/course pair, that pair is its key. If repeated enrolment events are allowed, an event identifier or another distinguishing attribute is needed. The story determines the key.

A relation’s schema names its attributes and domains. Its current instance is the set of rows currently stored. A superkey determines a row uniquely in every permitted instance; a candidate key is a minimal superkey. The chosen primary key is one candidate, not a claim that no others exist. A current sample with distinct names does not prove a name is a key. A declared rule must justify that conclusion.

Separate cardinality from participation

“Each order has one customer” supplies a many-orders-to-one-customer relationship. It does not mean every customer has an order. Total participation requires every entity of the relevant type to take part; it is a separate minimum requirement. For a many-to-many relationship, store a relationship table with foreign keys to the two entity tables. A multivalued attribute such as a person’s phone numbers normally needs its own table rather than a repeating cell.

A foreign key requires a child value to match a referenced parent key, subject to null rules and the declared delete/update actions. In today’s exercises, child foreign keys are NOT NULL and parent deletion uses RESTRICT: you cannot remove a referenced parent until the references are dealt with. Inserting a valid new parent cannot itself make an existing child reference point to a nonexistent parent. Deleting a child also cannot create that particular referential failure. Other constraints still need checking.

Choose types for meaning, not appearance

A phone number or postal code is usually an identifier, even when it contains digits. Numeric arithmetic can lose leading zeros. Fixed-precision DECIMAL is appropriate when exact decimal amounts matter; binary floating point need not represent values such as0.1 exactly. NOT NULL, CHECK, UNIQUE, PRIMARY KEY and FOREIGN KEY express different rules. SQL UNIQUE handling of nulls can vary by system, so questions that require a unique non-null identifier should state both uniqueness and NOT NULL.

Classical relational algebra uses sets; SQL query results usually retain duplicates unless DISTINCT or a set operation removes them. We will keep that distinction explicit on Days2–3.

Two worked examples

Make the relationship visible

A person may join many clubs and may have many phone numbers. Each club has many people. Map to relations; membership has at most one row per person/club pair.

Use Person(PersonID,…), Club(ClubID,…), Membership(PersonID,ClubID,…) with composite key(PersonID,ClubID), and Phone(PersonID,PhoneNumber) with a suitable pair key. Four relations separate entities, the many-to-many relationship, and the multivalued attribute. Total participation, if required, is an additional rule; it does not eliminate these structures.

Check an update, not a slogan

Customer IDs are{1,2}. Order rows(OID,CID) are(10,1),(11,1). CID is NOT NULL, a foreign key with RESTRICT. Can Customer1 be deleted?

No: both orders still reference1. Customer2 can be deleted because no order references2, assuming no other constraints. Inserting Customer3 is safe with respect to this foreign key, while inserting Order(12,3) is unsafe until parent3 exists.

B01-Q1

A and C. Candidate keys are minimal superkeys; a primary key is selected from them. A sample may happen to contain unique names without enforcing name uniqueness. A foreign key need not be unique in the child table.

First step: Distinguish schema constraints from the observed instance.. Diagnostic tag: key-definition. Likely trap: sample-versus-rule.

B01-Q2

A, B and D. A new parent12 cannot invalidate references; deleting a child removes a reference; unreferenced parent8 can be removed. Parent4 remains referenced.

First step: List surviving references after each operation independently.. Diagnostic tag: foreign-key-update. Likely trap: parent-child-direction.

B01-Q3

Four relations:Member keyed by MemberID; Book keyed by ISBN; Borrows(MemberID,ISBN) keyed by that pair; MemberEmail(MemberID,Email) keyed by the pair if duplicate emails per member are disallowed. The relationship and multivalued attribute each get a relation.

First step: Identify entities, many-to-many relationships, and repeated attributes separately.. Diagnostic tag: er-mapping. Likely trap: multivalue-in-one-cell.

B01-Q4

{EID} and{Email} are candidate keys. (EID,DeptID) is a superkey but not minimal, since EID alone suffices; it is not a candidate key. No uniqueness of DeptID is implied.

First step: Remove each extra attribute and check whether uniqueness remains.. Diagnostic tag: minimal-key. Likely trap: superkey-versus-candidate.

B01-Q5

Use a character type for the postal identifier, an appropriate DECIMAL(p,2) for exact decimal currency, and a numeric/integer quantity with NOT NULL plus CHECK(quantity>=0). A numeric type alone does not require presence or nonnegativity.

First step: Identify identity, arithmetic and domain rules separately.. Diagnostic tag: data-type-constraint. Likely trap: digits-imply-numeric.

Targeted repair

If a key answer used only sample values, restate the allowed-instance rule. If a foreign-key operation was reversed, draw arrows from child values to parent keys.

A fresh check

Does total participation of students in Enrolment mean each student can take only one course?

Check after trying

No. Total participation requires at least one relationship; maximum cardinality is a separate constraint.
