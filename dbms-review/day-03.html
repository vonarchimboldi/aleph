Follow the rows through the query

For the queries here, think in this logical order: FROM/JOIN forms candidate rows, WHERE keeps rows whose condition is TRUE, GROUP BY forms groups, HAVING filters groups, SELECT builds output columns, then DISTINCT/ordering may apply. This is a reasoning model for results, not a claim that the engine must physically execute in that order.

Ordinary SELECT keeps duplicates. A join can multiply rows: if a customer has three matching orders, the customer appears in three joined rows. A left join also retains an unmatched left row, with nulls in the right columns. COUNT(*) counts every result row; COUNT(right_key) counts only non-null right keys. Their difference matters on those unmatched rows.

NULL is not a hidden ordinary value

NULL represents missing or unknown information. Ordinary comparisons to NULL yield UNKNOWN rather than TRUE or FALSE. WHERE and HAVING keep only TRUE. Use IS NULL to test nullness. COUNT(column), SUM and AVG ignore null inputs; COUNT(*) does not. AVG divides by the count of non-null inputs, not the number of stored rows. SUM or AVG over no non-null inputs is NULL, not automatically zero.

NOT IN is dangerous when its subquery can return NULL. If no equality matches but one comparison is unknown, the negated membership test is still not TRUE, and the row is filtered. A correlated NOT EXISTS query can express the intended anti-match more directly, but explicitly decide whether null keys should qualify before calling the two queries equivalent.

Groups and correlated subqueries are different levels

WHERE filters individual rows before grouping. HAVING tests an aggregate property of a group. A correlated subquery contains a reference to the outer row, so its relevant comparison set can change for each row. To evaluate it on paper, write the outer ID and the subquery result side by side. This prevents the mistake of computing one global average when the query asks for a department average.

Always state ties and comparison direction. “Above average,” “at least average,” and “strictly more rows above than below” can select different records. ORDER BY is needed when output order matters; without it, a correct result set does not imply a guaranteed presentation order.

Two worked examples

Count the right objects

Sale(ID,Dept,Amount) has(1,A,10),(2,A,20),(3,B,20),(4,B,NULL),(5,C,5). Compute COUNT(*), COUNT(Amount), SUM(Amount), AVG(Amount).

The counts are5 and4. SUM is55, and AVG is55/4=13.75. The missing amount contributes neither a numeric value nor an extra denominator term to AVG.

A correlated comparison

For those sales, select rows whose Amount exceeds the average Amount of their own department.

Department averages are A15,B20,C5. Only ID2 has amount strictly above its local average. The null amount at ID4 fails the comparison. ID3 equals, rather than exceeds, B’s average; a global average would answer another question.

Text version of the mind map
  • Rows first: Join multiplicity; outer rows; SQL usually keeps duplicates.
  • Groups next: COUNT/SUM/AVG inputs; WHERE rows; HAVING groups.
  • Unknown values: IS NULL; comparisons UNKNOWN; Only TRUE survives filtering.
